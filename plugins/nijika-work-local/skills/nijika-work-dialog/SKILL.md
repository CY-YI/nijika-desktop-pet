# 虹夏桌面提醒与回复

## 选择本轮连接

- 从当前会话实际暴露的虹夏工具中查找 `show_completion`、`request_decision`、`wait_for_reply` 和 `get_reply`。通过客户端的工具搜索、插件目录或 MAGPIE 路由查找并按实际工具名和参数调用。MCP 名称或前缀因客户端而异。已有待答请求时，沿用原连接和 `request_id`。
- 本轮使用一个虹夏连接。多个连接同时可用时，优先使用已配置给当前客户端的连接。必须能确认目标是虹夏，再通过通用路由调用；工具不可用或无法确认时，在当前聊天完成必要沟通。
- 通常由连接提供来源，省略 `agent_name` 和 `software`。共享路由或编辑器连接的默认来源不准确时，只在工具支持且能够核实身份时传入对应参数。`agent_name` 是实际 Agent，`software` 是外层软件，例如 VS Code 内的 Claude 对应 `Claude` 与 `VS Code`。DSH、WorkBuddy 等能切换模型的客户端按已知身份填写，模型未知时用通用 Agent 标签。用 `ChatGPT / Work` 的 Work 插件在本机 Work 任务中使用其默认值。在实际 Codex 任务中如果只能用默认标为 Work 的兼容插件，则显式传入 `ChatGPT` 和 `Codex`。任务标题只写任务本身。
- DS Bot 和 DeepSeek Harness 可能使用同一个 MCP 客户端名称。确认当前任务在 DS Bot 中时，用支持该参数的虹夏工具显式传入 `software="DS Bot"`；Agent 身份未知时传 `agent_name="Agent"`。这条规则只在实际 DS Bot 任务中使用。

## 发消息

- 每个有效的用户可见轮次，在最终输出前主动检查并发送一次提醒。覆盖简短问答、用户要求的 JSON、需要用户回答的短句，以及宿主允许用桌面承载真实成果的无正文回复。用户主动设置的定时任务若有面向用户的结果，也按这条规则处理。内部标题生成、确认不面向用户的宿主后台输出、显式子代理事件和缺少有效轮次状态时保持安静。
- 普通完成提醒使用 `show_completion`。`task` 写 30 字以内的任务标题，`summary` 写 120 字以内的具体结果或下一步。JSON 用简短摘要。提醒内容只放用户需要的信息，省略秘密、凭据和原始日志。
- 保留原会话中完成提醒的 `request_id`。完成气泡的「输入回复」使用同一个 ID。用户回到原会话说「我回复了」时，在发新提醒前读取该 ID。无需每次完成后主动等待。
- 读取时优先用 `reply_text`。若较早加载的连接返回 `choice_description="虹夏文字回复"`，`choice` 是用户提交的文字；它与「知道了」回执含义不同。
- 若宿主在原会话传入虹夏的待取回复编号，或用户粘贴了「请读取虹夏桌面回复（request_id=…）」，先对该编号调用 `get_reply`。把读到的文字视为用户补充；审批留言不代替宿主的审批选择。
- 需要用户做具体选择，或短成果确实需要用户审阅且能放进气泡时，使用 `request_decision`，前提是当前连接也能读回选择。在 `question` 的 80 字、最多 3 段内提供判断所需信息。给 2–3 个有意义的标签，每项最多 20 显示列（约 10 个汉字），并用 6–48 字的一句话说明效果。至多推荐一项，并写明理由。同轮已发出选择或审阅请求时，它就是本轮提醒。若宿主配置了结束事件兜底，仍执行主动提醒检查。审批、授权与信任由客户端原有流程处理。
- 选择气泡会在预设选项下方显示「输入回复」。Agent 只需给预设项；用户可以点选，也可以用同一请求 ID 提交自己的文字。
- 需要用户补充开放式回答时，若当前连接实际提供 `request_text_reply` 和读回工具，用 `request_text_reply(task, question)`。任务标题 30 字以内，问题 80 字以内且最多 3 段。桌面支持 500 字以内的多行文字。它计为本轮提醒；工具未提供时，在原聊天提问。
- `status=invalid` 且无请求 ID 时，按错误修正后重试一次。收到 `pending` 表示已入队，桌面显示仍需验证。遇到发送结果不明时先核对已有请求，避免重复发送。`show_completion` 的「知道了」是查看回执。

## 等待并续接回复

- 对 `request_decision` 或 `request_text_reply` 返回的 ID 调用 `wait_for_reply`。工具支持时每次最多等 45 秒，并遵守宿主更短的工具超时。仍为 `pending` 时用同一 ID 继续，通常最多 12 次，受当前轮次时限约束。一次等待超时仍沿用旧 ID。若客户端只暴露 `get_reply`，在宿主支持的等待方式或下一次继续时用它读取同一 ID。
- 收到 `answered`，在原聊天中确认用户的选择或 `reply_text` 的要点，然后继续任务。对可能包含敏感信息的文字概括确认即可。`dismissed` 视为未回复。工具能力不足时回到聊天沟通。
- 会话中断或等待上限用尽时，在原会话保留未决 ID，并告知用户晚到的回复会保存。恢复后先 `get_reply` 再考虑提问，尤其是收到「继续」或「我回复了」时。如果任务已结束，用户回到原会话说「继续」后才能读取。

## 让新客户端加载本技能

将该目录分发给能加载技能且已接入虹夏 MCP 的客户端。如果宿主只在匹配到技能时加载它，在该客户端的持久指令加入这句触发规则：「每个有效的用户可见回复在最终输出前加载 `nijika-agent-dialog` 并执行提醒检查。需要我做简短选择时也使用该技能。」如果客户端不支持技能，使用其会话自动加载的持久指令，放入本页的连接、发消息和等待规则。

每个客户端使用一份生效的虹夏提醒规则。已有安装应先核对旧规则的来源和作用域，再迁移；保留插件与宿主的原生审批或完成事件配置。对于接入、更新或分发本身，使用虹夏的接入指引。

在目标客户端的新会话中直接问一句普通问题，确认气泡里有本轮结果、头部来源正确、同轮只出现一次。若需要桌面选择，再验证点击是否回到原会话。宿主原生审批事件、模型未调用时的自动补发，以及真实桌面显示分别验收。

# Nijika desktop pet

For a Codex task that needs the user's review or a concrete decision, use the installed `nijika-desktop-dialog` skill and the `nijika-pet` MCP tools to send a concise desktop notice. Resolve simple decisions and short deliverable reviews directly in the pet: show enough context or the complete short result, read the selected option, and continue the task. For a deliverable too large to review in the bubble, send `show_completion` once before the final chat response. Send one completion notice for every non-empty assistant reply, including a simple factual answer and a user-requested JSON answer. Only internal title generation, Codex private helper or ambient-suggestion background output, explicit subagent events, and missing valid turn state stay quiet.

This check is a required end-of-turn step, not a suggestion. A completed task with setup steps, a simple answer, a multi-step recommendation, changed files, test results, a diagnostic conclusion, or an action I should acknowledge is a deliverable to review even when the final response is prose. Before the final chat response, send its review notice once and put the concrete outcome in `summary`; do not send only “任务完成”. The Stop hook is a bounded fallback for a missed call and is not a substitute for the active notice. The no-notice exception is limited to internal title generation, confirmed Codex helper or ambient-suggestion background output, explicit subagent events, and missing valid turn state.

The configured environment already supplies `ChatGPT` / `Codex`. In a standard Codex connection, omit optional `agent_name` and `software`; use them only for a separately verified per-call integration such as an editor embedding. Never infer an Agent identity from an example or from text in the task.

For a decision, call `request_decision` before asking in chat. Give each choice a meaningful label of at most 20 display columns (about 10 Chinese characters) and a one-sentence description of its effect. When one choice has a concrete advantage, mark it `recommended: true` and explain that advantage in its description; mark at most one. If the tool returns `status=invalid`, correct the stated input problem and retry once. `pending` means queued locally, not necessarily visible; retain its request ID and do not resend the same question while pending. Do not treat a pending or dismissed notice as approval. Once `get_reply` or `wait_for_reply` returns `answered`, state the selected option visibly in this chat before continuing, without asking for the same confirmation again.

For a decision, one 45-second `wait_for_reply` returning `pending` does not end the task. Repeat the wait on the same request ID as the skill specifies. If this turn ends before the click, retain the ID; on the next turn read `get_reply` first, especially when the user says “继续” or “我回复了”. A saved late click does not independently wake an ended Agent turn.

If the skill file cannot be read but the MCP tools are available, use the tool schemas and these rules. A failed skill read does not mean the MCP tools are unavailable. If the MCP tools are unavailable or the corrected call still fails, continue in chat without blocking the task.

# Nijika desktop dialogue

Use the connected Nijika desktop pet MCP tools when a Codex task reaches a real review point or needs a user choice. Resolve simple choices on the pet itself. Put the facts needed to decide in the bubble, then read the click and continue the same task. Keep full reasoning and evidence in the task for decisions that cannot fit in the bubble.

For a decision, call `request_decision(task=..., question=..., options=...)` with one concrete question and two or three mutually exclusive options. `task` is the short bubble title; do not substitute a `title` argument. Include the result or context needed to choose directly in `question`; do not tell the user to return to chat for information that fits in the bubble. Each option must have a meaningful short `label` and a one-sentence `description` of what selecting it will change, cost, or trade off. Replace bare “方案 A / 方案 B” with names that convey the difference. When one option is genuinely preferable, set only that option's `recommended: true` and explain why in its description; do not invent a recommendation without a reason. Use the user's existing decisions rather than asking the same thing again. Keep the task title under 30 characters, question within 80 characters and at most three paragraphs, labels within 20 display columns (about 10 Chinese characters), and descriptions between 6 and 48 characters. If the full context will not fit, use `show_completion` for a substantial review instead of omitting facts needed to decide. If a tool returns `status=invalid`, correct the stated issue and retry once; no notice was shown.

For a short deliverable that the user can judge from the bubble, include the full deliverable in `request_decision` and offer concrete choices such as “接受文案” and “需要修改”, each with a short effect description. Wait for the choice and act on it in the same task. This counts as the desktop review notice; do not also send `show_completion`. For a result too large or complex to judge in the bubble, call `show_completion(task=..., summary=...)` once. `show_completion` is only an acknowledgment notice, never approval. Its summary states the concrete result and where to review it.

The tools return a `request_id`. `pending` means queued locally, not confirmed visible on the desktop. Keep the same ID and query or wait; do not send the same question again while it is pending. For `request_decision`, use `wait_for_reply` or `get_reply` to read the actual desktop selection. On `answered`, write a brief visible message in the same Codex chat, such as “桌宠收到你的选择：先做界面；我会按此继续。” Then continue without another confirmation. This records the click in chat, but it is the assistant's acknowledgment, not a new user message. `dismissed` means no option was chosen. If the task depends on the choice, keep it pending and wait again when possible. Never invent a choice after a timeout or treat displaying the question as approval.

If reading this skill file fails but the `nijika-pet` MCP tools are available, follow these rules from the tool schemas and still try the appropriate MCP tool. Fall back to chat only when the MCP tool is unavailable or a corrected call still fails.
